## 需求理解

一句话：希望把 UniFi Access 接入平台做成一个 MCP/integration，让 agent 既能读取门禁数据/状态，也能执行开门等动作，从而不用再手动在 UniFi Access 的界面或 API 里操作。

内部团队/客户需要 agent 在真实 workflow 里读取 UniFi Access（门禁系统）的数据/状态并执行开门等动作。今天的替代方式是人工在 UniFi Access 的 UI 或 API 里操作。需求方在访谈中明确表示"读"和"动作"两部分要一起交付，不分阶段（Interview Log 原话："If only one part could be built first, which smallest slice helps most? → All at the same time."）。成功的标准是 agent 能在真实 workflow 里用上这个集成、不再需要人工兜底。具体先支持哪些门/工作流、哪个租户/controller，需求方尚未回答 Triage Advisor 的追问（见 Open Questions）。

## 产品设计

### 目标 / 非目标

**目标**：
- 平台新增一个 UniFi Access 的 vendor MCP 连接器，租户可在 Integrations 里填写自己的 UniFi Access 本地控制器地址与 API Token 完成连接。
- Agent 能读取：门（door）清单与状态（锁定/解锁、在线状态）、访问事件/日志（谁在何时以何种方式尝试开门、结果）。
- Agent 能执行：解锁（unlock）指定的门。
- 交付后，内部团队/客户在真实 workflow 里查门禁状态或开门不再需要手动打开 UniFi Access 的 UI 或 API。

**非目标（本次不做）**：
- 不做"锁门"（lock）动作——UniFi Access 官方 API 本身不提供单门 lock 命令（只有 unlock 与整站 lockdown），这是能力边界，不是遗漏。
- 不做用户/权限/排班（schedule）等管理面的写操作——需求原话聚焦"读取数据/状态"+"执行开门等动作"，管理面属于更大的范围，留给后续迭代。
- 不做整站紧急模式（lockdown/evacuation）的写操作——影响全部门禁点、破坏性极高，MVP 不纳入写权限范围（见 Open Questions，后续如需要应作为独立单并配更强的确认机制）。
- 不做云端 UniFi Access API——公开资料显示这是纯本地控制器架构，没有已知的云端 API 可用。
- 不做 UniFi Network / Protect——那是姊妹单 PRD-17725 及其它潜在单的范围，本单明确只做 Access。

### 验收标准 AC1..ACn

- AC1: Given 租户已在 Integrations 页面为 UniFi Access 填好本地控制器地址与 API Token 并成功连接，When 打开该连接器详情页，Then 状态显示 Connected 且工具列表非空（复用平台既有连接器详情页机制，本单不需要新开发前端）。
- AC2: Given 已连接的 UniFi Access 连接器，When agent 调用"列出门"工具，Then 返回该租户控制器上的门清单，每条含门名称、id、当前锁状态；控制器没有门时返回空清单而不是错误。
- AC3: Given 一扇已知的门，When agent 调用"读取该门最近的访问事件"工具，Then 返回该门最近的访问尝试记录，含时间、尝试人（如可得）、认证方式、结果（granted/denied）；结果条数受合理上限约束，超出时明确告知还有更多。
- AC4: Given 一扇已知的、处于锁定状态的门，When agent 调用"解锁该门"工具并指定门 id，Then 该门被解锁，且随后再次读取门状态能看到已变为解锁。
- AC5: Given 凭据缺失或无效，When agent 调用任意工具，Then 收到结构化的、不包含凭据本身的错误说明，而不是裸异常或未分类的 500。
- AC6: Given 一个不存在的门 id，When 调用解锁工具，Then 返回明确的"资源不存在"错误，不会误操作到别的门、也不会静默成功。
- AC7: Given 两个不同租户各自的凭据（各自指向自己的 controller），When 分别调用同一个只读或写工具，Then 每次请求只会作用于该请求自带凭据所指向的那个 controller，不存在"用租户 A 的凭据看到或操作租户 B 数据"的路径。

## 技术设计

### 结论

新建 `unifi-access-mcp`（Python 3.12 + uv + FastMCP，照抄 `ninjaone-mcp` 的自建单 Header-Bearer-Token 直连模式）实现门禁读 + 单门解锁的 MCP Server；在 `mcp-service-gateway` 的 `vendor/registry.yaml` 追加一条 `source: self_built` 的 vendor 条目完成网关侧注册。两个仓库是两次独立、可分别验收的改动——`unifi-access-mcp` 是主体工作量，`registry.yaml` 只是几行配置追加，这样最省，因为完全复用了已验证过的自建 vendor MCP 套路（`ninjaone-mcp`）和网关侧现成的注册机制，不需要发明新模式。

### 方案选型

只有一个显然的方案：照 SOP 与 `ninjaone-mcp` 的形状自建，不做基于开源实现的移植。理由：WebSearch 确认不存在 `wyre-technology/unifi-access-mcp` 这类官方支持的开源实现；社区里唯一现成的是 `hjdhjd/unifi-access`（非官方 TypeScript 库），它的定位是"补足官方 API 之外的完整能力"，直接搬用会引入未经我们验证的行为，且与本单"先对接官方支持的最小可用面"的诉求不符。结论：直接实现一个薄封装，只包一次 UniFi Access 官方 Bearer Token API，不引入第三方库。

### 数据与接口契约

MCP 工具契约（暴露给 Agent 的接口，本设计自己定义，authoritative）：

- `unifi_access_list_doors() -> str`：无参数。成功返回 `{"doors":[{"id":str,"name":str,"lock_state":"locked"|"unlocked"|"unknown"}],"has_more":bool}`。字段名是本设计假设，需开发棒对照真实 controller 核实（见 Open Questions）。
- `unifi_access_get_door(door_id: str) -> str`：返回单门详情；`door_id` 不存在时返回 `not_found` 错误信封。
- `unifi_access_list_access_events(door_id: str | None = None, limit: int = 50) -> str`：`limit` 默认 50、硬上限 200（SOP §2.5）；成功返回 `{"events":[{"time":"<iso8601>","door_id":str,"actor":str|null,"method":str|null,"result":"granted"|"denied"}],"has_more":bool}`。
- `unifi_access_unlock_door(door_id: str) -> str`：写操作，`destructiveHint=True`；成功返回 `{"door_id":str,"unlocked":true}`；`door_id` 不存在返回 `not_found`。

错误信封统一遵守 SOP §4.2 固定词表：`not_configured` / `unauthorized` / `not_found` / `invalid_argument` / `rate_limited` / `upstream_error`（各自的 `retryable` 取值照 SOP 表格）。

Header 凭据（SOP §3.1 命名规范 `X-<Vendor>-<Credential>`）：

| Header | 必填 | 含义 | 在哪里申请 |
|---|---|---|---|
| X-UniFi-Access-Host | 是 | 控制器地址，如 https://192.168.1.1 或域名 | 客户自己的 UniFi Access 控制器 |
| X-UniFi-Access-Token | 是 | 控制器生成的 API Bearer Token | 控制器 Web UI：Access > Settings > General > Advanced > API Token |
| X-UniFi-Access-Verify-Ssl | 否 | 默认 true；控制器常见自签名证书场景，允许按需关闭校验（README 需标注风险） | — |

`mcp-service-gateway/vendor/registry.yaml` 新增条目（描述性示例，实际改动由开发棒完成）：

```yaml
  - name: unifi-access
    repo_url: https://github.com/MSPbotsAI/unifi-access-mcp.git
    port: 8080
    health_path: /health
    display_name: UniFi Access
    source: self_built
    credential_fields:
      X-UniFi-Access-Host:
        label: Controller Host
        required: true
        example: https://192.168.1.1
      X-UniFi-Access-Token:
        label: API Token
        type: password
        required: true
        example: your-api-token
      X-UniFi-Access-Verify-Ssl:
        label: Verify SSL Certificate
        required: false
        default: "true"
        enum: ["true", "false"]
```

向后兼容：全新集成，无老数据、无老客户端需要兼容。

### 关键流程时序

通用请求路径：Agent → Gateway（按租户注入 Header）→ `unifi-access-mcp` → UniFi Access 本地控制器 REST API → 返回 → `unifi-access-mcp` 结构化 → Gateway → Agent。

解锁流程：
1. Agent 调用 `unifi_access_list_doors` 确认目标 `door_id`。
2. Agent 调用 `unifi_access_unlock_door(door_id)`。
3. `unifi-access-mcp` 用当前请求 contextvar 里的 Host/Token 直接向控制器发起 unlock 请求。
4. 控制器返回成功/失败，映射为 SOP 错误信封或 `{"door_id":...,"unlocked":true}`。
5.（可选）Agent 再调用 `unifi_access_get_door` 或 `unifi_access_list_doors` 确认门状态已变化。

### 非功能

- 幂等与并发：对同一 `door_id` 重复调用 `unlock` 预期是安全的（门已解锁再解锁一次，结果仍是"已解锁"而非错误）——`idempotentHint` 待开发棒用真实 API 验证幂等行为后再决定是否标注。请求级凭据用 `contextvars` 隔离（SOP §3.3），不做跨请求缓存（SOP §3.4）。
- 性能：门禁场景数据量小（单租户门数量预期在几十量级），不需要额外的分页优化，但仍遵守 `limit` 默认 50/硬上限 200 与单次返回 ≤20000 字符（SOP §2.5）。出站超时 5s/30s，单次工具调用总耗时含重试 <120s（SOP §5）。
- 安全：Token 只从 Header 读、不落盘不落环境变量（SOP §3.1）；`unifi_access_unlock_door` 标 `destructiveHint`、只接受明确 `door_id`、不接受批量（SOP §2.7）；错误 `message` 不回显 Token（SOP §4.2/§11）；关闭 DNS-rebinding 保护是安全的，因为服务不直接对外暴露（SOP §7）。
- 多租户隔离：本服务无状态、无本地存储，每次请求的 Host+Token 就是租户身份本身——不存在"服务端保存了租户 A 的门列表又返回给租户 B"的路径，因为从不缓存（对应 AC7）。
- 可观测：结构化日志记工具名、`door_id`（非敏感）、controller 返回状态码、耗时、错误 code；不记 Token（SOP §6）。

- TC1 · AC1 · 手工：Given 租户已按 README 表格填好 Host/Token 并保存，When 打开 UniFi Access 连接器详情页，Then 状态为 Connected 且 Tools 列表非空。
